# Inventory Replenishment Planner

Plan next week's inventory replenishment from transaction history. The planner forecasts sales for 24 SKUs and recommends whole-unit orders within a shared purchasing budget. Enter current stock, purchase costs, shortage penalties, and holding costs to see the recommended quantities, total spending, and projected unmet units.

## Run locally

From the repository root, with Python 3.12 and curl installed:

```sh
scripts/run setup
scripts/run fetch
scripts/run prepare
scripts/run verify
scripts/run serve
```

## Compare order plans

Open [the local API explorer](http://127.0.0.1:8000/docs). `GET /demo` provides a sample request with assumed opening stock and per-item costs. Copy the `request` object to `POST /plan`, then run it again with `budget_cents` reduced from `2800000` to `1400000`. Compare spending, order quantities, and projected unmet units. For a custom plan, select any subset of the trained SKUs and enter your own values. Money is expressed in integer cents.

`GET /forecast` shows all three models' forecasts and identifies the default. Supply `"forecast_method": "gradient_boosting"` in a plan request to use the trained model. `GET /health` returns readiness and the loaded artifact's SHA-256. To update the sales history, prepare the new input and restart the service. Load only model artifacts generated by this project.

The default working directory is `../work`. It holds the SQLite database, the model, the EDA plot and summary, and the forecast and policy results. Set `PLANNER_WORK` to use a different directory. `scripts/run verify` runs the unit tests and starts and restarts a temporary API instance to check forecast loading, budget changes, request validation, and the trained model route.

## Data and evaluation

The source is [UCI Online Retail](https://doi.org/10.24432/C5BW33), a UK retailer's transaction history licensed under CC BY 4.0. The loader reads 541,909 rows, retains 528,886 merchandise sales rows, and reconciles 5,645,020 retained units against SQLite. It excludes returns, cancellations, and rows outside the product-code format. The database retains SKU, date, and quantity.

SQL groups transactions into Monday-start weeks, adds zero-sales weeks for the selected SKUs, and drops the first and last source calendar weeks. The 24 SKUs are chosen by transaction-day frequency in the training period. The prepared report covers 1,248 SKU-weeks.

Two observations matter to the order decision:

- Median weekly sales across the selected SKUs rose from 6,747 in the first eight weeks to 10,913 in the last eight. This series covers one retail year. Use a changing weekly forecast and verify the seasonal pattern on more years before relying on it for long-range purchases.
- Median SKU-week sales were 232 units and the 90th percentile was 740. Removing the largest SKU-week shifts the 90th percentile to 738. High-volume weeks are widespread enough to warrant checking order quantities and budgets across multiple weeks.

Validation and testing each cover eight subsequent weeks. The model uses only earlier sales and known calendar features. The four-week mean was selected on validation MAE and scored **181.85 units MAE** per SKU-week on the 192 held-out predictions. Gradient boosting scored **227.66**, and last-week persistence scored **225.54**. The four-week mean underpredicted by **22.00 units per SKU-week** on average. Both data preparation and forecast evaluation ran on macOS and Linux.

## Order planning and limits

The solver chooses whole units to minimize expected shortage penalties plus holding costs, subject to the purchase budget. The comparison rule orders by largest forecast unit deficit. Both policies start with the same simulated stock, use the same forecasts and budget, receive orders immediately, and carry unused stock forward. Unmet units are treated as lost sales in the simulation.

In the eight-week scenario, optimized ordering reduced the simulated penalty-plus-holding cost by about **18.85%**. It filled **45.9%** of units versus **49.8%** for the comparison rule. The chosen penalty schedule rewards filling some SKUs ahead of others. A planner who cares most about total fill should adjust the objective or compare the policies before choosing. The Linux run differed by about 0.01 percentage points in optimized fill.

Recorded sales are a proxy for demand. The public source provides no stock ledger or supplier constraints. The simulation assumes same-week receipt and excludes lead-time variability, minimum order quantities, and observed operating costs. The results describe this scenario.
